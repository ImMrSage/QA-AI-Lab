# Инструменты API, безопасность и стратегия тестирования

## Часть 3: инструменты

Используйте коллекции и переменные окружения Postman для связанных запросов, curl — для воспроизводимых HTTP-примеров, OpenAPI — для контрактов, JMeter — для контролируемой генерации трафика.

| Потребность | Инструмент или артефакт | Вопрос проверки |
| --- | --- | --- |
| Исследовать связанные запросы | Коллекция Postman | Проверяются значения и эффекты или только статус? |
| Переключать окружения | Именованные переменные | Выбрано нужное окружение, секреты исключены из экспорта? |
| Воспроизвести запрос | Команда curl | Удалены учётные данные и подходят правила кавычек оболочки? |
| Описать HTTP API | Описание OpenAPI | Соответствует работающая реализация заявленному контракту? |
| Смоделировать трафик | План JMeter | Репрезентативны интервалы, данные и критерии отказа? |

OpenAPI описывает HTTP API; Swagger — семейство инструментов. Описание можно написать заранее или сгенерировать из кода. Генерация не гарантирует точность и не исключает недокументированное поведение. См. [спецификацию OpenAPI](https://spec.openapis.org/oas/latest.html).

Переносы строк curl в источнике зависят от оболочки. В Windows используйте нужный исполняемый файл и синтаксис оболочки. Копирование запроса не гарантирует воспроизведение при других учётных данных, данных или окружении. Команды источника не выполнялись против удалённого API.

## Часть 4: безопасность и архитектура

Источник различает идентификацию, аутентификацию и авторизацию, объясняет серверные сессии с cookies и кеширование, вводит REST, SOAP/WSDL и тестовые двойники. В примере stub возвращает погоду, а mock проверяет взаимодействия отправки почты.

| Граница | Практическая проверка |
| --- | --- |
| Аутентификация | Отсутствующие, просроченные и отозванные учётные данные |
| Авторизация | Чужой объект и роль без разрешения |
| Жизненный цикл сессии | Ротация после входа, инвалидирование при выходе и тайм-аут |
| Область cookies | Domain, path, Secure, HttpOnly и SameSite |
| Изоляция кеша | Ответы одного пользователя не утекают другому |
| Тестовый двойник | Проверка поведения потребителя и совместимости с реальной зависимостью |

POST не гарантирует конфиденциальность: тела могут попадать в логи. HTTPS защищает транспорт, а не всё поведение приложения. Прикрепление cookies зависит от области действия и политики браузера, а не просто от «каждого запроса к серверу». Приватный режим не эквивалентен любому состоянию нового пользователя. Аутентификация и авторизация — разные проверки, а не обязательная трёхшаговая последовательность каждого запроса.

Statelessness REST относится к состоянию диалога сессии, а не запрещает хранить ресурсы. SOAP — протокол сообщений, не ограниченный по природе HTTP POST; WSDL описывает контракт сервиса. Stub предоставляет управляемые ответы; взаимодействия можно проверять mocks или spies в зависимости от фреймворка. Успех изолированных тестов не доказывает корректность интеграции.

Настройки cookies и жизненный цикл описаны в [OWASP Session Management](https://cheatsheetseries.owasp.org/cheatsheets/Session_Management_Cheat_Sheet.html). HttpOnly ограничивает доступ из скриптов, но не останавливает любой вредоносный аутентифицированный запрос. SameSite — дополнительный уровень защиты, а не универсальная замена защиты от CSRF.

## Часть 5: автоматизация и диагностика

Источник предлагает регрессионную, smoke- и data-driven автоматизацию, сравнивает несколько стеков, описывает плавный рост, постоянную, ступенчатую и пиковую нагрузку, load/stress/soak/volume-тестирование, затем разбирает белый экран после входа.

Уточнения: поведение UI можно автоматизировать, хотя оценке удобства нужно человеческое суждение. У smoke-набора нет универсального обязательного размера. Тестирование производительности — общее понятие; нагрузочные тесты выявляют и функциональные дефекты. Одновременные пользователи и запросы в секунду — разные величины. Статус не доказывает, кто виноват; успешный ответ входа не проверяет последующие запросы.

### Авторская таблица диагностики

| Наблюдение | Следующие свидетельства |
| --- | --- |
| Нет запроса входа | Ошибка консоли, обработчик события, клиентская валидация |
| 4xx | Контракт, учётные данные, права и ответ посредника |
| 5xx | Correlation ID, здоровье зависимостей и серверные логи |
| 2xx, но белый экран | Схема ответа, редиректы, cookies, последующие запросы и ошибки рендеринга |

Запишите минимальное воспроизведение, скрыв секреты. Ответственность компонента должна быть выводом из свидетельств.

### Авторский чек-лист планирования нагрузки

Определите набор бизнес-транзакций, конкурентность или интенсивность поступления, интервалы, данные, длительность, перцентили задержки, допустимые ошибки и ожидания восстановления. Записывайте потребление ресурсов генератора, чтобы не принять его насыщение за предел сервиса. Используйте разрешённое тестовое окружение и сохраняйте неудачные ответы для диагностики. JMeter рекомендует CLI для запуска нагрузки: [лучшие практики](https://jmeter.apache.org/usermanual/best-practices.html).
