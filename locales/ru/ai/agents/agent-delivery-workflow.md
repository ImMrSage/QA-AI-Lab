# Процесс доставки изменений с AI-агентами

Выдача инструмента генерации кода не устраняет ожидание требований, ревью и релиза. Стандартизируйте переходы между этапами: какие данные нужны на входе, какой артефакт остаётся на выходе и кто принимает результат.

## Путь изменения

```mermaid
flowchart LR
 A[Задача и критерии] --> B[Нужные документы]
 B --> C[План по риску]
 C --> D[Реализация в отдельной среде]
 D --> E[Проверки обещанного поведения]
 E --> F[Ревью и CI]
 F --> G[Проверка кандидата в staging]
 G --> H[Доставка через разрешённый процесс]
 H --> I[Наблюдения и обновление знаний]
 I --> A
```

## Роли документов

| Артефакт | На какой вопрос отвечает |
| --- | --- |
| Корневая инструкция | Куда идти и какие ограничения соблюдать? |
| Архитектура и контракты | Как устроена система и что она обещает? |
| План изменения | Что меняем и как докажем готовность? |
| ADR | Почему выбран этот вариант? |
| Рабочий навык | Как повторить процедуру? |
| Исполняемая проверка | Как обнаружить нарушение автоматически? |
| Runbook | Как диагностировать и восстановить работу? |

Храните общие знания отдельно от адаптера конкретного агента. У важных документов должны быть область действия, владелец, статус и повод пересмотра. Не дублируйте механически сведения, которые уже можно извлечь из кода.

## Пример для QA AI Lab

Учебная задача: добавить фильтр инструментов по назначению. Обещание: фильтр показывает подходящие инструменты, смена языка сохраняет выбор, сброс возвращает полный список.

| Этап | Предлагаемый артефакт для Lab |
| --- | --- |
| Постановка | Три наблюдаемых ожидания и определение смешанной категории |
| Контекст | Файлы каталога, логика фильтра и правила переводов |
| План | Малый diff, состояния пустого результата и сброса |
| Проверка | Пример одной категории, смешанной карточки и смены языка |
| Ревью | Сверка исходных ожиданий с diff и реальным поведением |
| Доставка | Коммит и результат разрешённого pipeline |
| Обратная связь | Ошибки, время до принятия и обновлённое правило |

Это предложение по организации будущей задачи; перечисленные проверки не заявлены как уже внедрённые.

## Критерий готовности и эффективность

Результат готов к приёмке, когда есть проверяемый артефакт, свидетельства выполнения исходного обещания и список оставшихся ограничений. Ревью должно опираться на требования и реализацию, а не только на убедительный отчёт исполнителя.

Для пилота возьмите один повторяемый тип задачи. Раздельно измеряйте время работы и ожидания, долю возвратов, стоимость проверки и дефекты после принятия. Сравнивайте задачи сходного объёма; скорость генерации и число PR не показывают, сколько полезного результата принято.

Сильную или дешёвую модель выбирайте по результатам конкретных задач и цене ошибки. Отдельная модель-ревьюер может повторять ошибки исполнителя; проверяемые ожидания остаются необходимыми. Воспроизводимая среда может быть контейнером или другим подходящим решением, но её границы доступа должны быть определены явно.
