# QA-агент с инженерным контуром доказательств

## Стройте систему проверки, а не идеальный промпт

QA-агент получает неполные и противоречивые данные. Его задача — восстановить явную модель приёмки, собрать независимые свидетельства, показать неопределённость и оставить решение уполномоченному человеку. Убедительный текст не является доказательством.

## Архитектура

| Слой | Ответственность |
| --- | --- |
| Рабочие инструкции | Обязательный порядок, определения, стандарт доказательств и условия остановки |
| Skills | Повторяемые процессы для требований, кода, API, БД, UI и отчёта |
| Rules | Разрешения, подтверждения, секреты, политика публикации и границы |
| Конфигурация проекта | Репозитории, окружения, сервисы, роли, разрешённые действия и места артефактов |
| Детерминированные инструменты | Анализаторы, API/DB/UI-исполнители и валидаторы схем |
| Артефакты и обратная связь | Планы, наблюдения, отчёты, исходы, паттерны дефектов и проверенные уроки |

Имена проектов, endpoints, роли и статусы трекера храните в конфигурации. Секреты держите вне конфигурации и версионируемых артефактов. Переносимому ядру всё равно нужен адаптер для каждого реального трекера или сервиса.

## Цепочка доказательств

1. Соберите задачу, родителя, комментарии, вложения, решения, код и предыдущие результаты.
2. Запишите обязательное постусловие каждого критерия до того, как реализация станет восприниматься как требование.
3. Зафиксируйте источник и наблюдение, способное подтвердить или опровергнуть постусловие.
4. Проследите затронутый код и выберите проверки по риску.
5. Запустите детерминированные API-, read-only DB- и UI-проверки там, где каждый слой даёт независимое свидетельство.
6. Соберите матрицу: критерий → источник → факт из кода → исполненное наблюдение → пробел → вывод.
7. Верните **выполнено**, **не выполнено** или **недостаточно доказательств** и точный ручной чек-лист.

Успешный HTTP-ответ может доказать приём запроса, но не сохранение состояния и не поведение для пользователя. Если БД недоступна, фиксируйте пробел доказательства persistence, а не выдумывайте дефект продукта.

## Контролируемые действия

- Разделяйте чтение, локальное создание артефакта, изменение тестовой среды и внешнюю публикацию.
- По умолчанию разрешайте БД только для чтения; запись выдавайте отдельным узким профилем.
- Когда этого требует политика, запрашивайте подтверждение для комментариев и статусов в tracker, Git-записи и значимых действий в среде.
- Не помещайте credentials в планы, отчёты, репозитории и накопленные паттерны.
- Считайте отказ инструмента ограничением выполнения, пока поведение продукта независимо не докажет дефект.
- Агент может выбирать следующую разрешённую проверку; организационную приёмку выполняет её владелец.

## Память процесса

Сохраняйте проверенные исходы вне весов модели: рекомендацию, решение человека, пропущенный факт, урок и сигнал для будущей проверки. Прошлый паттерн порождает гипотезу, но текущие свидетельства должны подтвердить её заново. Версионируйте артефакты и происхождение, чтобы ревьюер мог восстановить причину изменения процесса.

## Оценка

Измеряйте возвраты задач после рекомендации агента, пропущенные факты, ложные тревоги, долю критериев с независимым исполняемым доказательством, время до первой полезной находки, повторные классы дефектов и трудозатраты человека. Confidence требует эмпирической калибровки; без неё используйте состояния доказательств вместо декоративных процентов. Сравнивайте пилот с подходящим baseline и учитывайте состав задач, изменения среды и зрелость команды.
