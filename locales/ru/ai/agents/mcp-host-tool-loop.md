# MCP и цикл вызова инструментов в хосте

## Основной цикл взаимодействия

Дмитрий Боровик показывает, как приложение получает предложенную моделью операцию запроса погоды, вызывает MCP-сервер и возвращает результат модели. Полезное различие — модель предлагает операцию, а код хоста выполняет её. Статья вводит tools, resources, prompts, sampling, roots и elicitation.

Это самостоятельное изучение AI и разработки приложений со связью с Tools. Подход применим к личным помощникам, инструментам разработки игр и учебным приложениям наряду с QA-инструментами.

## Уточнения протокола

По явно версионированной схеме MCP 2025-11-25 используйте `sampling/createMessage`, `elicitation/create` и `notifications/message`; чтение ресурса — `resources/read`. Несколько названий в статье отличаются. Sampling — запрос под контролем клиента, а не безусловная возможность расходовать токены. Roots описывают область файловой системы; перечисление пути само по себе не выдаёт разрешений ОС. Важны версия и согласованные возможности.

JSON провайдера модели в статье — иллюстрация, а не обязательный API модели в MCP. Утверждения о всегда корректных аргументах и взаимоисключающих текстовом/инструментальном ответах не должны становиться допущениями хоста. Валидируйте каждую запрошенную операцию.

## Практическое проектирование: авторское упражнение

| Этап | Ответственность хоста |
| --- | --- |
| Обнаружение | Зафиксировать схемы доступных инструментов |
| Получение предложения | Проверить имя, аргументы и область |
| Выполнение | Применить разрешения и тайм-аут |
| Возврат свидетельств | Сопоставить каждый результат с вызовом |
| Продолжение | Ограничить повторы вызовов и общую стоимость |

Создайте помощника только для чтения и поиска личных проектных заметок. Проверьте неизвестные инструменты, неверные аргументы, недоступные серверы и вводящий в заблуждение текст результатов до добавления записи.
