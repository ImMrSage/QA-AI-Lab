# AI в ежедневной работе QA

AI помогает готовить черновики, исследовать варианты и собирать повторяющиеся действия. QA задаёт ожидаемое поведение и проверяет результат. Редактирование полезного черновика может экономить время; исправление слабого иногда обходится дороже самостоятельной работы.

## 11 сценариев и проверка результата

Матрица сохраняет сценарии статьи; критерии приёмки сформулированы для практического использования в Lab.

| Задача | Что поручить AI | Что проверить |
| --- | --- | --- |
| Тест-кейсы | Черновик по описанию функции | Ожидания подтверждены требованиями; дубликаты убраны |
| Анализ сценария | Пропущенные условия и риски | Гипотезы отделены от правил продукта |
| Интеграции | Варианты сбоев взаимодействия | Таймауты, повторы, дубли и порядок соответствуют контракту |
| Настройка инструментов | Объяснение команды или конфигурации | Версия, параметры и эффект понятны до запуска |
| Тестовые данные | Позитивные, негативные и граничные наборы | Ограничения, валюты, округление и локаль заданы явно |
| SQL | Запрос по вопросу и схеме | JOIN, NULL, часовой пояс и фильтры дают ожидаемые строки |
| Логи | Гипотезы и следующий диагностический шаг | Причина подтверждена воспроизведением или свидетельством |
| Баг-репорт | Структуру из наблюдений QA | Нет придуманных шагов, окружения или ожидаемого результата |
| Автотесты | Небольшой тест на существующих фикстурах | Сохранены стиль проекта, изоляция и смысл assertions |
| Падение UI-теста | Исследование DOM и локатора | Исправление сохраняет целевой элемент и исходную проверку |
| Проверки страницы | Сценарии для выбранных элементов | Область задана явно; проверяется результат действия, не только клик |

## Пример задания агенту

Для учебного сценария изменения адреса доставки:

> Используй приложенные правила валидации и существующий тест редактирования профиля. Предложи три проверки изменения адреса: успешную, невалидный индекс и отказ сохранения. Для каждой укажи ожидаемое состояние интерфейса и данных. Неизвестные правила оформи вопросами. Сначала покажи план, затем небольшой diff; не ослабляй assertions ради зелёного результата.

Скриншот с отмеченными элементами помогает задать область исследования. Он не определяет бизнес-правила и не доказывает полное покрытие страницы. Проверка всех видимых кнопок оставляет за пределами состояния, роли, данные и отказы.

## Приёмка результата

1. Дайте агенту релевантные требования, версию инструмента и пример из проекта; уберите секреты из логов и данных.
2. Проверьте черновик на предположения и соответствие задаче.
3. Запустите запрос или тест на подходящем тестовом окружении.
4. Сверьте наблюдаемое поведение с независимым ожидаемым результатом.
5. Сохраните принятый артефакт и зафиксируйте фактические затраты, включая перепроверку.

Приведённые автором минуты — личные оценки, не воспроизведённый benchmark. Обновление локатора допустимо после проверки поведения: падение может указывать на дефект продукта, а не на устаревший тест. Подключение Playwright MCP само по себе не подтверждает корректность ремонта.

## От требований к проверенным тестам

Кейс Дениса Тальстюка связывает анализ требований, согласование проверок и автоматизацию. Недоступная ссылка не доказывает отсутствие требований.

| Этап | Результат |
| --- | --- |
| Анализ | Вопросы по противоречиям, границам, дизайну и зависимостям |
| Согласование | Чек-лист передачи разработки; отдельные регрессионные кейсы |
| Автоматизация | Тесты в существующей архитектуре; ревью ассертов |
| Контекст | Краткий индекс и документы, читаемые по задаче |

Команды задают повторяемый запрос, субагенты выделяют контекст, MCP предоставляет инструменты. Фидбэк сохраняют правилами, но повторное испытание необходимо. OCR, координаты и негативные проверки требуют особого внимания. Совет агентов не заменяет ревью человека. Это описание подхода, не внедрение интеграций.
