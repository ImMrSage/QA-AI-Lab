# Проверка API-запроса

Используйте вместе с [основами запросов REST API](../../qa/api-testing/rest-api-request-basics.md). Это вопросы для проектирования проверок; ожидаемые результаты берите из контракта endpoint и требований продукта.

- [ ] Уточнить окружение, метод, путь и query-параметры.
- [ ] Проверить обязательные заголовки, схему тела и типы данных.
- [ ] Выполнить допустимый запрос и проверить фактические возвращённые значения.
- [ ] Вместе проверить статус, заголовки, схему и бизнес-эффекты.
- [ ] Покрыть отсутствующие, пустые, некорректные и граничные значения, где применимо.
- [ ] Проверить доступ без учётных данных, с неверными данными и ID чужого ресурса.
- [ ] Сверить неизвестные ID и неподдерживаемые методы с контрактом.
- [ ] Для изменений подтвердить сохранённое состояние подходящим независимым чтением.
- [ ] Учесть дублирующие отправки и повторы изменяющей состояние операции.
- [ ] Для асинхронных операций отдельно от принятия проверить итог.
- [ ] Убедиться, что ошибки не раскрывают секреты и внутренние детали реализации.
- [ ] Сохранить воспроизводимые свидетельства без секретов и очистить тестовые данные.

Чек-лист дополняет проверки конкретного endpoint; он не обеспечивает полное покрытие безопасности или производительности.

## Проверки по методам

| Операция | Дополнительные проверки |
| --- | --- |
| POST | Все поля и только обязательные; пропущенные поля; пустой объект и отсутствие тела; типы, границы, дубликаты, временные метки, сохранённый результат |
| GET | Пустые и заполненные коллекции; допустимые, неизвестные и неверные ID; фильтры, сортировка, границы пагинации |
| PUT | Контракт полной замены; пропущенные поля; отсутствующий ресурс; уникальность; итоговое состояние |
| PATCH | Поддерживаемый формат; целевые изменения; незатронутые значения; неверный patch и конкурентные изменения |
| DELETE | Существующий, отсутствующий и уже удалённый ресурс; зависимые записи; повторное создание, если поддерживается |

- [ ] Проверить медиатипы, локализацию при необходимости и значимые заголовки запроса/ответа.
- [ ] Измерить время ответа и конкурентность по согласованным целям в подходящем окружении.
- [ ] Проверить доступные логи и корреляцию, защищая чувствительные данные.

## Уточнения, зависящие от контракта

Источник считает частичный PUT и сохранение пропущенных полей общими ожиданиями. PUT описывает замену; используйте фактический контракт и отличайте PATCH. Отрицательный offset не всегда означает первую страницу, а неверная пагинация не всегда требует 400. Запишите выбранное поведение API. Повтор DELETE может вернуть другой статус, сохранив ожидаемый эффект. Не требуйте XML или каскадного удаления без спецификации.
