# Системная отладка: от сбоя к проверяемой причине

Наблюдаемый сбой — начало расследования. Выдвигайте гипотезу о первом неверном состоянии, выбирайте различающий эксперимент и только затем меняйте реализацию.

```mermaid
flowchart LR
 A[Сбой пользователя] --> B[Зафиксировать входы и среду]
 B --> C[Найти первое неверное состояние]
 C --> D[Гипотеза причины]
 D --> E[Различающий эксперимент]
 E -->|Не подтвердилось| C
 E -->|Подтвердилось| F[Исправление и регрессионная проверка]
```

## Выбор наблюдения

| Условия | Следующий шаг |
| --- | --- |
| Стабильно воспроизводится | Сузить входы, проследить изменение значения |
| Доступны только артефакты | Сопоставить хронологию, dump и точную сборку |
| Зависит от расписания | Наблюдать потоки и синхронизацию, контролировать порядок |
| Отличается между средами | Сравнить конфигурацию, ABI, зависимости и данные |
| Есть у QA, нет локально | Совместно повторить исходный сценарий до переписывания кода |

Цепочка defect → infection → failure разделяет дефект, неверное внутреннее состояние и видимый сбой. В статье пример с хешированием padding показывает, почему равные логические ключи не должны получать разные хеши из-за представления памяти.

## Карточка гипотезы — рабочий шаблон

1. Факт: какой результат отличается от требования? Указать идентификатор запуска.
2. Гипотеза: какое условие могло породить первое расхождение?
3. Прогноз: что должно измениться при контролируемом изменении одного входа?
4. Эксперимент: разрешённая среда, конкретное наблюдение, критерий опровержения.
5. Итог: факт, исключённые варианты и следующая проверка; отдельно от предположений.

Пример QA Lab: таблица выходит за контейнер только при масштабировании. Зафиксировать viewport, zoom и измеренные границы; проверить ту же страницу с теми же данными при другом масштабе. Если переполнение исчезло, это сужает гипотезы, но ещё не доказывает конкретную CSS-причину.

Для гонок breakpoint может менять расписание. Повторяемость после искусственной задержки усиливает гипотезу, но не доказывает её сама по себе. Ожидание futex не означает deadlock без анализа зависимостей. Контейнер не воспроизводит чужое ядро ОС; для таких различий нужна подходящая VM или реальная система. После исправления проверить исходный сбой и соседние сценарии; отсутствие сбоя в одном запуске недостаточно.
