# HTTP-статусы: проверки и ловушки

## Главное
Проверяйте точный код, заголовки, данные и побочные эффекты по контракту API. Совпадение класса ответа — слабая проверка, если контракт обещает конкретный статус.

## Карта статусов
| Класс | Смысл | Что проверить |
| --- | --- | --- |
| 1xx | Промежуточная информация | Не принять за завершение операции |
| 2xx | Успешная обработка на уровне HTTP | Данные, изменения состояния; 202 ещё не результат задачи |
| 3xx | Перенаправление или условное использование кэша | Location, метод перехода; 304 без тела |
| 4xx | Запрос не может быть выполнен в представленной форме | Контракт ошибки и отсутствие нежелательных изменений |
| 5xx | Сервер не выполнил запрос | Диагностика зависимостей, поведение клиента |

## Практическая матрица
| Сценарий | Коды для различения | Проверка сверх числа |
| --- | --- | --- |
| Создание или фоновая задача | 201 / 202 | Созданный ресурс либо последующее завершение задачи |
| Ответ без содержимого | 204 | Тело отсутствует |
| Кэш | 304 | Условный запрос и повторное использование сохранённого представления |
| Перенаправление | 301 / 302 / 303 / 307 / 308 | Цель и цепочка переходов; 307/308 сохраняют метод, 301/302 могут изменить POST на GET |
| Доступ | 401 / 403 / 404 | 401 требует WWW-Authenticate; 403 не доказывает аутентификацию; 404 может скрывать ресурс |
| Метод и формат | 405 / 415 / 422 | Allow при 405; неподдерживаемый формат отдельно от семантики данных |
| Конфликт | 409 | Состояние ресурса и отсутствие частично выполненной операции |
| Ограничение частоты | 429 | Область лимита, восстановление и ограниченные повторы |
| Сбой инфраструктуры | 500 / 502 / 503 / 504 | 502 — некорректный ответ upstream, 504 — ожидание upstream; проверить клиентскую обработку |

## Практические принципы
Статья охватывает коды, позитивные и негативные проверки, границы, rate limiting, заголовки и типичные ошибки. Инфографика полезна для запоминания классов, но подпись к 3xx чрезмерно обобщает поведение: 304 не требует обычного перенаправления.

Не задавайте универсальные ожидания «пустое тело → 400» или «отрицательное число → 422»: сначала определите допустимые значения и контракт. 201 не привязан только к POST; Location не безусловно обязателен. 422 в RFC 9110 называется Unprocessable Content. HEAD не имеет тела; некоторые вычисляемые заголовки могут отличаться от GET. OPTIONS описывает возможности, а не гарантирует универсальный список методов.

Retry-After при 429 необязателен и не обещает точного сброса лимита. Заголовки X-RateLimit-* зависят от сервиса. Для 206 учитывайте различие одиночного диапазона и multipart-ответа. 101 относится к переключению протокола в HTTP/1.1; не переносите пример автоматически на все версии HTTP. 102 — специализированный код WebDAV, не обязательный сценарий обычного REST API.

## Рабочий пример
Для создания заказа запишите ожидаемый код из OpenAPI, схему тела и допустимые побочные эффекты. Повторите запрос без доступа, с неверным форматом и с конфликтующим идентификатором. После отказа проверьте, что заказ не появился. Для фонового ответа 202 отдельно наблюдайте конечное состояние задачи. Повтор после таймаута допускайте только с учётом идемпотентности: иначе возможно двойное создание.
