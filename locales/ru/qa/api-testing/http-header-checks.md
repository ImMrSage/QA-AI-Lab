# HTTP-заголовки: практические проверки API

Проверяйте ответ целиком: точный статус, заголовки, тело и изменение состояния. HTTP 200 не гарантирует успешный бизнес-результат; допустимость `success: false` определяется контрактом, а мониторинг должен видеть бизнес-отказы.

## Матрица заголовков

| Заголовки | Сценарий | Проверка |
| --- | --- | --- |
| Content-Type, Accept | Формат данных | Тип соответствует контракту; вместо JSON не пришёл HTML |
| Location | Создание, редирект | Адрес корректен; переход сохраняет нужный метод |
| Cache-Control, Vary | Повторный запрос | Нет смешивания пользователей и вариантов ответа |
| ETag, Last-Modified | Условное чтение | Валидатор соответствует версии ресурса |
| Set-Cookie | Сессия | Флаги, область действия, отправка браузером |
| WWW-Authenticate, Allow | 401, 405 | Присутствуют обязательные сведения |
| Retry-After | Ограничение, недоступность | Клиент соблюдает указанную задержку |
| Access-Control-* | Браузерный API | Preflight и фактический ответ разрешают нужный сценарий |

## Формат, создание и редиректы

Content-Type описывает представление; Accept выражает допустимые для клиента форматы. Проверяйте статус и фактическое тело до попытки JSON-разбора. Ответ 204 не содержит тела; сервер не должен отправлять в нём Content-Length, даже 0.

Для 201 адрес созданного ресурса определяется Location либо URI запроса. Location не безусловно обязателен; относительный адрес допустим. Проверьте доступ к созданному ресурсу по контракту. Для одиночного диапазона 206 нужен Content-Range; у multipart-ответа он находится внутри частей.

301/302 допускают смену POST на GET; 307/308 сохраняют метод. 303 направляет к чтению представления, обычно GET, также возможен HEAD. Нужный Location проверяйте как часть контракта редиректа, включая относительный адрес, цепочку и разрешённые внешние назначения: не всякий чужой домен является дефектом. Нежелательный переход, управляемый вводом пользователя, требует проверки на open redirect.

202 означает принятие к обработке. Отдельно проверяйте конечное состояние и отсутствие повторного списания. Idempotency-Key действует только при реализованном серверном контракте.

## Кэш и персональные данные

`no-cache` разрешает хранение с проверкой перед повторным использованием; `no-store` запрещает хранение. `private` исключает общий кэш; `max-age` задаёт свежесть, `s-maxage` — для общего кэша. Vary участвует в выборе варианта, но не заменяет политику защиты персональных ответов. Авторизованные запросы и cookies требуют анализа реальной конфигурации CDN и сервера.

Проверьте одним URL профиль пользователя A, затем B через тот же общий кэш: B не должен получить данные A. Затем повторите чтение с If-None-Match по полученному ETag: при совпадении ожидается 304 без тела, после изменения — актуальная версия. ETag может быть слабым или сильным; не требуйте одинаковой строки для разных представлений. If-Modified-Since — альтернативный сценарий с Last-Modified.

## Cookies и безопасность

Secure ограничивает отправку HTTPS, HttpOnly закрывает чтение из JavaScript, но не устраняет XSS. SameSite=None требует Secure. Для кросс-сайтового POST учитывайте SameSite, режим credentials и ограничения браузера; SameSite и CORS решают разные задачи. Проверьте Domain, Path, срок действия и удаление при logout. Несколько Set-Cookie сохраняйте отдельными полями, не объединяйте обычной запятой.

По требованиям проверьте HSTS, CSP, nosniff и защиту от встраивания через frame-ancestors либо X-Frame-Options. Наличие заголовка без подходящего значения недостаточно. В отчёт не включайте действующие cookie и токены.

## CORS в браузере

Для кросс-origin запроса с Authorization, JSON Content-Type или PUT обычно требуется preflight, если подходящее разрешение не закэшировано. OPTIONS проверяет разрешённые origin, метод и заголовки. Не требуйте пользовательскую сессию в preflight. После него проверяйте CORS-поля и фактического ответа: успешный OPTIONS не доказывает доступность результата для JavaScript.

При credentials нужен конкретный разрешённый origin и Access-Control-Allow-Credentials: true; wildcard origin не подходит. При динамическом выборе origin учитывайте Vary: Origin. Доступ JavaScript к нестандартным заголовкам ответа проверяется через Access-Control-Expose-Headers. Запрет чтения из-за CORS не доказывает, что сервер не выполнил запрос. Postman не заменяет браузерную проверку.

## Ошибки и повторы

401 требует WWW-Authenticate, 405 — Allow. 403 означает отказ выполнить запрос и не доказывает успешную аутентификацию. 404 может скрывать существование объекта. Retry-After при 429 или 503 не универсально обязателен; если он присутствует, принимает секунды или HTTP-дату. При отсутствии задайте ограниченную стратегию повторов по контракту. Не считайте любой 503 автоматически запрещённым к кэшированию: проверяйте явные директивы.

На 5xx проверьте отсутствие стека, SQL и путей в публичном ответе. Request-id помогает сопоставить ошибку с логами, если предусмотрен сервисом.

## Что сохранить в баге

- Метод, очищенный URL, время, окружение и шаги; статус и версию HTTP. Reason phrase не обязательна и отсутствует в HTTP/2 и HTTP/3.
- Значимые заголовки запроса и ответа, цепочку редиректов или OPTIONS, идентификатор запроса.
- Сырое тело с удалёнными секретами и персональными данными, ожидаемый контракт и фактические побочные эффекты.
- Для кэша — последовательность двух пользователей; для браузера — Network и наблюдаемую ошибку. HAR тоже нужно очистить от секретов.
