# Playwright на Python: от записи к проверке

## Главное
Урок показывает путь от записи действий к Python-тесту: локаторы, фикстуры pytest, Page Object, параллельный запуск и помощь AI. Главная практическая идея — переработать запись в проверку наблюдаемого результата. Успешные клики без assertions не доказывают правильность приложения.

## Выбор и ограничения
| Вопрос | Практический ответ |
| --- | --- |
| Playwright или Selenium? | Оцените поддерживаемые браузеры, инфраструктуру и существующие тесты; язык ядра не определяет качество тестов |
| Auto-waiting | Ожидает готовность элемента к конкретному действию, но не любое бизнес-событие; используйте повторяемые assertions |
| Locator | Описывает поиск заново при использовании; неоднозначный или неверный селектор всё равно сломает тест |
| Sync или async? | Sync удобен для последовательного pytest; async нужен при интеграции с asyncio, а не автоматически ради скорости |
| Jupyter | Полный запрет из урока неверен: async применим в совместимой среде; на Windows важна поддержка subprocess в event loop |
| Параллельность | pytest-xdist устанавливается отдельно и использует процессы; изоляция данных сервера остаётся вашей задачей |
| Браузеры | WebKit не равен установленному Safari; проверка движка не покрывает все особенности продукта Safari |
| Selenium | Поддерживает явные и неявные ожидания; сравнение «всё вручную против всё автоматически» слишком грубое |

## Локаторы и рабочий процесс
Начните с роли и accessible name либо label. Test ID полезен как согласованный контракт, но не является безусловно самым стабильным вариантом. Ограничивайте поиск контейнером. Позиция nth уместна, когда именно порядок является требованием; иначе она скрывает идентичность элемента.

Запись codegen → уточнение локаторов → явные проверки результата → повторяемые данные → Page Object при повторении действий → прогон и анализ ошибок. Page Object не обязателен для каждого маленького теста.

AI может предложить рефакторинг и локаторы, но проверяйте их на настоящем DOM. Передавайте только допустимый для передачи контекст. MCP даёт агенту инструменты браузера; сам по себе не гарантирует корректный тест.

## Минимальный пример
В отдельной учебной среде установите pytest-playwright, затем браузеры командой playwright install. Для параллельного запуска дополнительно нужен pytest-xdist. Корректное имя пакета — pytest-playwright; в глоссарии источника оно переставлено местами.

Сохраните пример как test_save.py и запустите pytest test_save.py. Это самостоятельный пример с локальным HTML, не E2E-проверка магазина из урока.
```python
from playwright.sync_api import Page, expect

def test_save(page: Page):
    page.set_content('<button onclick="this.textContent=\'Saved\'">Save</button>')
    page.get_by_role('button', name='Save', exact=True).click()
    expect(page.get_by_role('button', name='Saved', exact=True)).to_be_visible()
```

## Поправки и проверка понимания
В конструкции with sync_playwright() as p переменная p — объект Playwright, а не менеджер контекста; p.chromium — BrowserType. Фикстуры page/context помогают управлять жизненным циклом, но не очищают вашу внешнюю БД. Фиксированная пауза time.sleep не заменяет ожидание результата. Шаблон имени test_*.py — соглашение обнаружения pytest, которое можно настроить, а не единственное возможное имя файла.

Проверьте себя: какой результат докажет сохранение, что произойдёт при двух одинаковых кнопках и выдержит ли тест одновременный запуск с общими данными? Перед публикацией теста ответьте на все три вопроса.
