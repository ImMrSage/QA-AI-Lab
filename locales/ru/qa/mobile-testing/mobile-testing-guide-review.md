# Мобильное тестирование: проверенный разбор полного гайда

## Кратко

Исходный гайд — большая практическая карта мобильного тестирования: устройства и платформы, 17 направлений тестирования, 20 групп проверок, Charles Proxy, инструменты Android/iOS, типичные дефекты и справочник. Его лучше использовать как генератор идей, а не выполнять целиком для каждого релиза. Матрица должна строиться по аналитике пользователей, рискам изменения, поддерживаемым ОС, форм-факторам и возможностям устройства.

Полностью прочитан публично доступный текст страницы объёмом 53 284 символа, включая все семь разделов, таблицы, команды и глоссарий. Автор — Евгений Гусинец, канал QA❤️4Life. Дата публикации и лицензия на странице не указаны. Разбор сначала написан на русском, затем переведён на английский.

## Карта источника

| Раздел | Содержание | Что применять |
| --- | --- | --- |
| 1 | Устройства, типы приложений, версии ОС, дизайн-гайдлайны и аппаратная часть | Выбирать реальные конфигурации из продуктовой аналитики и требований поддержки |
| 2 | Функциональность, UI/UX, совместимость, сеть, прерывания, производительность, доступность, безопасность и фон | Формировать области риска и ожидаемое поведение |
| 3 | Подробные чек-листы от подготовки окружения до deep links, платежей и платформенных режимов | Адаптировать к функции, не переносить числовые пороги без требований |
| 4 | Настройка Charles, throttling, rewrite, SSL, редиректы, конкурентность, кэш и загрузка файлов | Использовать только в разрешённой тестовой среде и с тестовыми данными |
| 5 | Реальные устройства, эмуляторы, Android Studio, Xcode, профилировщики и device clouds | Сочетать быстрый виртуальный охват с доказательствами на реальных устройствах |
| 6 | Утечки, ориентация, сеть, WebView, push и синхронизация | Превращать типовые сбои в риск-ориентированные сценарии |
| 7 | Границы, HTTP, экраны, ADB, горячие клавиши, тест-план и словарь | Сверять с контрактом продукта и актуальной документацией платформы |

## Матрица покрытия

```mermaid
flowchart TD
    A[Функция и риск] --> B[Поддерживаемые ОС и target SDK]
    B --> C[Форм-факторы и размеры окна]
    C --> D[Состояния приложения и разрешений]
    D --> E[Сеть, фон и прерывания]
    E --> F[Доступность, локаль и производительность]
    F --> G[Набор устройств и доказательства]
```

Для каждого значимого сценария фиксируйте версию приложения и backend, устройство или профиль эмулятора, ОС/API level, состояние установки, аккаунт, разрешения, сеть, локаль, тему и энергосберегающий режим. Это делает дефект воспроизводимым и помогает отличить проблему приложения от среды.

## Главные поправки к гайду

| Утверждение или правило | Уточнение |
| --- | --- |
| iOS 16–18 и Android API 33–35 актуальны на 2026 год | Список устарел. Android 16 использует API 36, а Google Play с 31 августа 2026 требует API 36 для новых приложений и обновлений. Версии iOS нужно брать из текущей матрицы поддержки продукта и аналитики |
| React Native и Flutter — hybrid-приложения | Их обычно относят к cross-platform native frameworks; hybrid чаще означает web-контент в native-контейнере. Риски WebView и нативного рендеринга различаются |
| Проверять последние 2–3 ОС плюс самую популярную | Это стартовая эвристика. Учитывайте минимальную поддерживаемую версию, долю пользователей, target SDK, модели с высокой аварийностью и изменения платформы |
| Удаление приложения гарантирует «чистую» повторную установку | Keychain, облачные резервные копии, серверное состояние и некоторые идентификаторы могут сохраниться. Отдельно проверяйте локальное, облачное и серверное состояние |
| App Clip ограничен 10 MB | Лимиты менялись и зависят от версии ОС и типа invocation; проверяйте актуальные требования Apple для конкретной поставки |
| Любому Android-приложению достаточно установить CA Charles | Приложения с target Android 7+ по умолчанию не доверяют пользовательским CA. Нужна безопасная debug-конфигурация доверия; pinning и отдельные networking libraries могут по-прежнему блокировать перехват |
| Certificate pinning — обязательная универсальная защита | Android прямо предупреждает о рисках pinning и рекомендует предусматривать backup key. Решение принимает security/architecture с планом ротации |
| Фиксированные cold start <3 с, tap delay <100 мс, API <2–3 с и 60 FPS | Это возможные цели, но не универсальные критерии. Нужны продуктовый SLO, класс устройства, тип сети, сценарий запуска, percentile и метод измерения |
| У всех текстов контраст 4.5:1 | 4.5:1 относится к обычному тексту; для крупного текста допустим 3:1, а UI-компоненты и графика имеют отдельные требования WCAG |
| HTTP-метод или статус всегда имеет одно ожидаемое поведение | Контракт API определяет допустимые коды, идемпотентность и тело ответа. Повторный DELETE может вернуть 204, 404 или иной документированный результат |
| Повторить POST 5–10 раз и ожидать ровно одну запись | Это верно только при определённом контракте идемпотентности, например с idempotency key. Иначе несколько ресурсов могут быть корректным результатом |
| SQL/XSS/path-traversal строки можно применять как обычные данные | Это security-проверки. Выполняйте их только в разрешённой среде, в согласованной области и без риска повредить данные |
| Все регрессионные проверки обязательно выполнять на реальных устройствах | Нужен смешанный подход. Эмуляторы дают быстрый масштаб, а реальные устройства обязательны там, где важны аппаратные датчики, OEM-поведение, энергия, радиомодуль и фактическая производительность |

## Практический минимальный набор

1. Выберите устройства по доле пользователей и риску: минимум одна актуальная iOS-конфигурация, одна минимально поддерживаемая, несколько Android API/OEM и нужные форм-факторы.
2. Проверьте clean install, обновление с поддерживаемой предыдущей версии и восстановление состояния.
3. Пройдите критический путь при нормальной сети, затем при потере, задержке, переключении и восстановлении соединения.
4. Проверьте разрешение, отказ, ограниченный доступ, отзыв разрешения и возврат из Settings.
5. Проверьте foreground, background, terminated state, прерывания, deep links и push для поддерживаемых состояний.
6. Увеличьте системный шрифт, включите screen reader, тёмную тему, RTL/длинную локаль и внешнюю клавиатуру, если она входит в область.
7. Измеряйте запуск, отзывчивость, память, CPU, сеть и энергию на определённом классе устройства с повторяемым сценарием.
8. Перед выпуском повторите критический путь на реальных устройствах и зафиксируйте остаточный риск.

## Charles и сетевые проверки

Перехватывающий proxy полезен для наблюдения запросов, throttling и контролируемой подмены ответов. Не добавляйте доверие к тестовому CA в production-сборку. Для Android используйте debug-only Network Security Configuration; для iOS учитывайте ATS, pinning и поведение используемой библиотеки.

Проверяйте не только статус: метод, URL, заголовки, тело, аутентификацию, повтор, тайм-аут, кэш, редиректы, персональные данные и побочный эффект. Нагрузочные выводы по 50–100 запросам через Charles ограничены: для server-side capacity нужен отдельный инструмент и контролируемый профиль нагрузки.

## Чек-лист доказательств

- [ ] Матрица устройств опирается на поддержку, аналитику и риск.
- [ ] Указаны build, backend, ОС/API, модель и состояние установки.
- [ ] Для разрешений проверены grant, deny, limited, revoke и Settings.
- [ ] Состояние сохраняется при повороте, resize, фоне, убийстве процесса и нехватке памяти там, где это требуется.
- [ ] Offline/retry/sync не создают дубликаты и не показывают данные другого аккаунта.
- [ ] Accessibility проверена сервисами платформы, а не только визуально.
- [ ] Пороги производительности имеют условия и источник требования.
- [ ] MITM и инъекционные проверки выполнялись только в разрешённой среде.
- [ ] Известные пропуски и остаточный риск вошли в отчёт.
