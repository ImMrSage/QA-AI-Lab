# Качество ПО и измеримые критерии

## Кратко

Качество зависит от пользователей, назначения продукта и ограничений. Превратите потребность в явный критерий, затем соберите доказательства в заданных условиях. Успешные тесты подтверждают выбранные аспекты поведения, но не измеряют качество продукта целиком.

## Разбор источника

QA4Life рассматривает качество как соответствие контексту и перечисляет функциональную пригодность, производительность, совместимость, удобство использования, надёжность, безопасность, сопровождаемость и переносимость. Автор предлагает согласовывать измеримые цели, отслеживать динамику и пересматривать критерии при изменении контекста.

Эти восемь категорий описывают модель качества продукта **2011 года**. ISO отмечает эту редакцию как отменённую; **ISO/IEC 25010:2023 содержит девять характеристик**. Нельзя представлять список статьи как актуальную полную модель. Различие подтверждено официальными общедоступными описаниями; полный платный текст стандарта не изучался. [Модель 2011 года](https://www.iso.org/standard/35733.html), [модель 2023 года](https://www.iso.org/standard/78176.html).

## Составляем критерий — авторский шаблон

| Поле | Пример для вымышленного API поиска |
| --- | --- |
| Потребность пользователя | Результаты приходят достаточно быстро, чтобы продолжить покупки |
| Метрика | Полная задержка ответа и доля ошибок |
| Условия | Указаны сборка, среда, набор данных и состав трафика |
| Цель | Согласованный предел p95 и максимально допустимая доля ошибок |
| Окно | Определены длительность измерения и исключение прогрева |
| Доказательства | Отчёт о нагрузке, неудачные запросы и телеметрия сервиса |
| Решение | Назначенный ответственный оценивает сбои и остаточный риск |

Задавайте числовые ограничения после определения потребностей продукта и реалистичных условий эксплуатации. Сравнивайте результаты, полученные в сопоставимых условиях.

## Осторожно интерпретируйте метрики

| Упрощение источника | Более точная интерпретация |
| --- | --- |
| Фиксированные пределы задержки UI/API | Это примеры целей; нужны перцентиль, границы измерения и нагрузка |
| Успешны более 95% smoke-тестов | Один отказ критического сценария может блокировать релиз независимо от процента |
| Авторизация нужна всем эндпоинтам | Каждому нужна правильная политика доступа; некоторые намеренно публичны |
| Нет известных критических уязвимостей | Это полезное свидетельство, но не доказательство отсутствия неизвестных уязвимостей |
| RTO и RPO обозначают время восстановления | RTO относится ко времени восстановления, RPO — к восстанавливаемой точке данных и возможной потере данных |

### Пример доступности

Для расчёта по времени за год из 365 дней:

`365 × 24 × (1 − 0.999) = 8.76 часа`

При таком определении 99,9% соответствует примерно 8 часам 46 минутам недоступности. В реальном соглашении могут использоваться другое окно, исключения или измерение по запросам. Процент без знаменателя и правил расчёта неполон.

## Практическое применение

Для нашей библиотеки оценивайте вместе успешность чтения, релевантность поиска, читаемость мобильной вёрстки и точность содержания. Быстрая страница с неверным объяснением всё равно означает проблему качества. Запишите небольшой набор согласованных критериев и доказательства по каждому вместо объединения несвязанных показателей в необъяснённый общий балл.
